## What it means

Gall’s law favors evolving complex working systems from simpler working systems over attempting a complete complex design in one leap. It is a systems-design heuristic associated with John Gall’s Systemantics, rather than a proof that all successful systems share one history. [Gall, General Systemantics, original book record](https://books.google.com/books/about/General_Systemantics.html?id=6FgeAAAAMAAJ).

The important word is **working**. A set of polished components that has never completed a real workflow provides less evidence than one small, coherent path through the actual system.

## Worked example

Imagine building an enterprise knowledge agent. The grand design includes many data connectors, autonomous tools, multi-tenant permissions, billing, and a visual workflow builder. Developing all of those in parallel delays discovery of whether users can get a useful, authorized answer.

A smaller first system can support one tenant, one approved document collection, and one read-only retrieval tool. It still authenticates the user, checks access, records outcomes, and handles a missing answer. That complete path exposes retrieval quality and permission problems early.

The next increment might add a second data source. Another introduces a carefully scoped action with confirmation and an audit trail. Each step preserves the working behavior and creates evidence for the next decision. This is an illustrative sequence, not an account of an employer’s implementation.

## Put it to work

Choose a vertical slice around a valuable user outcome. Include enough operational behavior to know whether it works: logs, failure states, a repeatable evaluation, and a way to roll back. Avoid calling a static demo a working production system.

Keep boundaries that allow likely changes without building every hypothetical extension. A simple tool contract and a replaceable storage interface may be useful. A general plugin marketplace before the first reliable workflow may be premature.

Add complexity in response to observed needs and measured limits. Before adding a queue, explain what work needs asynchronous handling. Before splitting a service, explain which ownership or scaling problem the split solves. Preserve a record of those decisions so later maintainers understand the constraints.

## Limits and misuses

Incremental evolution does not guarantee that an early design will scale forever. A one-tenant assumption can become an expensive obstacle if the product already requires tenant isolation. Some constraints must be planned before the first release.

The heuristic also does not eliminate migrations or deliberate redesign. When a boundary is wrong, change it with a transition plan and evidence. The goal is frequent contact with a functioning system, not preserving every early implementation choice merely because it worked once.
