## What it means

Gall’s law favors evolving complex working systems from simpler working systems over attempting a complete complex design in one leap. It is a systems-design heuristic associated with John Gall’s Systemantics, rather than a proof that all successful systems share one history. [Gall, General Systemantics, original book record](https://books.google.com/books/about/General_Systemantics.html?id=6FgeAAAAMAAJ).

The important word is **working**. A set of polished components that has never completed a real workflow provides less evidence than one small, coherent path through the actual system.

## AI agent example

Start with a knowledge agent for one team and one approved document collection. It authenticates the user, retrieves permitted passages, produces an answer with evidence, and handles missing information. That is a complete narrow workflow.

Evaluate it with real questions before adding many connectors. If it cannot distinguish an unsupported answer from a supported one, a larger tool catalog will not solve that gap automatically.

Next, add another collection and test cross-source questions and permission boundaries. Introduce a read-only operational tool when there is a clear user need. Add a state-changing action only after the workflow can authorize, confirm, audit, and recover that action.

This sequence is illustrative. Some requirements, such as tenant isolation in a product that already serves multiple organizations, must shape the first design rather than being deferred as future complexity.

## Before you build

Choose a vertical slice defined by a user outcome. Include the failure path, identity boundary, trace, and evaluation needed to judge it. Preserve a working baseline as capabilities expand.

Add orchestration complexity in response to observed task needs. A multi-agent coordinator, general workflow builder, or plugin marketplace should solve a demonstrated limitation. Keep migration paths open when evidence shows an early boundary needs to change.

**Design decision:** Before building a general agent platform, prove one narrow workflow works under realistic success and failure conditions.

## Limits and misuses

Incremental evolution does not guarantee that an early design will scale forever. A one-tenant assumption can become an expensive obstacle if the product already requires tenant isolation. Some constraints must be planned before the first release.

The heuristic also does not eliminate migrations or deliberate redesign. When a boundary is wrong, change it with a transition plan and evidence. The goal is frequent contact with a functioning system, not preserving every early implementation choice merely because it worked once.
